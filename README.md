# Обед вместе

Сервис коллективного заказа обедов в офис: сотрудники выбирают блюда по общей ссылке, а поставщик проверяет переводы, принимает доставку и ведёт возвраты. Заявки и статусы сохраняются в PostgreSQL: сотрудники со своих устройств видят общий ход сбора. У каждого сотрудника своя заявка, привязанная к cookie его браузера.

Стек: React 19, Vite 8, Node.js 24, Express 5, PostgreSQL 17 и Docker Compose. В production один контейнер приложения обслуживает интерфейс и API, второй хранит базу. API описан в [API-CONTRACT.md](API-CONTRACT.md), эксплуатация — в [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## Локальная разработка

Нужны Node.js 24 или новее, npm и Docker с Compose.

```sh
npm ci
npm run setup
npm run db:dev
```

Дождитесь готовности PostgreSQL: `docker compose -p lunch-together-dev -f compose.yml -f compose.dev.yml ps` должен показывать `healthy`. Затем:

```sh
npm run dev
```

Интерфейс: `http://localhost:5173`, API: `http://localhost:3000/api/health`. Vite перенаправляет `/api` на Express. База разработки опубликована только на `127.0.0.1:55435`.

`npm run setup` создаёт `.env` и `work/supplier-access.txt` с правами `600`, не перезаписывая существующий `.env`. Логин и первоначальный пароль поставщика находятся в `work/supplier-access.txt`; вход — `/#supplier`. Пароль можно сменить в кабинете: после смены потребуется войти заново на всех устройствах.

## Полностью в Docker

Если ранее запущена база разработки, сначала остановите её стек без удаления тома: обе конфигурации используют одну фиксированную подсеть.

```sh
docker compose -p lunch-together-dev -f compose.yml -f compose.dev.yml down
```

Для новой установки сначала выполните `npm run setup`, если `.env` ещё не создан. Затем:

```sh
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
```

Открыть `http://localhost:3080`; проверка базы и API — `http://localhost:3080/api/health`. По умолчанию приложение слушает порт `3080` на всех интерфейсах; доступность с телефона зависит от сети и правил доступа к компьютеру. PostgreSQL не публикует порт на хосте. Данные находятся в именованном томе `lunch-together_postgres_data` и переживают пересоздание контейнеров.

## Как устроен заказ

1. Сотрудник выбирает блюда, указывает имя и при необходимости отдел. Регистрация не нужна. Менять или отменять неоплаченную заявку можно до срока приёма заказов.
2. После достижения минимума участников открывается оплата. Участник переводит деньги непосредственно поставщику по его реквизитам и нажимает «Я перевёл».
3. Поставщик вручную сверяет поступление и подтверждает либо отклоняет перевод. Нажатие сотрудника переводит заявку только в статус проверки.
4. Когда набрано достаточно оплаченных порций и разобраны все переводы на проверке, поставщик принимает заказ. В приготовление входят только оплаченные позиции.
5. При отмене сбора оплаченные заявки переходят в ожидание возврата. Поставщик возвращает деньги отдельно и отмечает результат в кабинете. Старые сборы и незакрытые возвраты доступны ему через историю.

Платёжного шлюза, автоматического списания, проверки банковских переводов и автоматических возвратов нет. Сроки и переходы статусов проверяет сервер. Указанное время относится к Алматы (UTC+5).

Первый запуск пустой базы создаёт поставщика и пример меню из трёх блюд на следующий день по Алматы, без вымышленных участников и оплат. Это настоящий сбор в базе, а не сценарий, который автоматически сбрасывается. Перед показом сотрудникам поставщик отменяет первоначальный сбор и публикует новый: задаёт меню, цены, адрес, реквизиты, сроки и минимумы. Каждый следующий сбор создаётся после принятия или отмены предыдущего.

Cookie сотрудника действует 180 дней; сессия поставщика — 7 дней. Заявка сотрудника доступна только в исходном браузере: другой телефон, другой домен или очистка cookie не восстанавливают её по имени. Публичный API не отдаёт имена и отделы других участников; поставщик видит заявки после входа.

## Проверки

```sh
npm run check
npm run build
docker compose -f compose.test.yml up -d --wait db
TEST_DATABASE_URL='postgresql://lunch_test:disposable_test_password@127.0.0.1:55436/lunch_test' npm test
docker compose -f compose.test.yml down
```

Тестовый Compose создаёт отдельный PostgreSQL с данными в tmpfs и портом только на loopback. Интеграционные тесты проверяют владение заявками, авторизацию, ручные оплаты, возвраты, сроки и конкурентные изменения на настоящем PostgreSQL. Без `TEST_DATABASE_URL` интеграционный тест пропускается. Не направляйте его на рабочую базу.

## Настройки и доступ

`.env`, `work/`, зависимости и результаты сборки исключены из Git. В `.env.example` находятся только примеры. Не коммитьте и не публикуйте `.env` или `work/supplier-access.txt`.

В базе хранится scrypt-хеш пароля поставщика и хеши токенов сессий. Первоначальный пароль записывается только в локальный закрытый файл доступа. `SUPPLIER_LOGIN` и `SUPPLIER_PASSWORD_HASH` используются при создании первого поставщика; изменение этих переменных не меняет пароль уже существующей учётной записи.

Серверный адрес приложения и порядок безопасного обновления описаны в [инструкции развёртывания](docs/DEPLOYMENT.md). Домен и сертификат подключает владелец; для рабочего входа поставщика используйте HTTPS.
