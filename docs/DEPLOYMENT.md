# Развёртывание «Обед вместе»

Эта инструкция описывает отдельный стек `lunch-together`. Он использует собственные контейнеры, сеть и PostgreSQL; соседний стек libnode менять или перезапускать не нужно. Наличие инструкции само по себе не подтверждает выполненное развёртывание: состояние проверяется командами ниже.

## Сервер и порты

| Параметр | Значение |
| --- | --- |
| SSH | `qustust@100.126.73.77` |
| Каталог проекта | `/home/qustust/projects/lunch-together` |
| Compose project | `lunch-together` |
| HTTP-порт приложения | `3080` |
| Upstream для host Nginx | `http://127.0.0.1:3080` |
| Docker subnet | `172.16.80.0/24` |
| Docker gateway | `172.16.80.1` |
| Доверенный proxy | `172.16.80.1/32` |
| Том PostgreSQL | `lunch-together_postgres_data` |
| Общая maintenance-блокировка | `/home/qustust/projects/libnode-backups/automatic/.automation.lock` |

Приложение публикует `0.0.0.0:3080 → 3000`; PostgreSQL доступен только внутри Docker. `APP_PORT` и `BIND_ADDRESS` меняют публикацию HTTP-порта. Пара `LUNCH_SUBNET`/`LUNCH_GATEWAY` позволяет выбрать другую непересекающуюся сеть; при смене gateway нужно одновременно изменить `TRUST_PROXY` и проверить доставку заголовков от proxy.

`172.30.0.0/16` уже используется соседним стеком на этом сервере. Перед созданием новой сети проверяйте актуальные Docker IPAM и маршруты, сохраняя чужие сети.

## Подготовка и первый запуск

Исходники должны находиться в каталоге проекта на проверенном commit из `git@github.com:MadiTurkmenbay/lunch-together.git`. Если серверу недоступен GitHub, доставляйте тот же commit через Git bundle. Не применяйте `reset --hard`, `clean` или принудительную перезапись к checkout с чужими изменениями.

На машине с Node.js 24 выполните `npm ci` и `npm run setup` в checkout. Setup создаёт закрытые `.env` и `work/supplier-access.txt`; существующий `.env` он не заменяет. Доставьте нужный `.env` на сервер защищённым способом с правами `600`, не выводя содержимое в терминал, отчёты или Git. Пароль поставщика передавайте владельцу отдельно из файла доступа. Для Docker используются `POSTGRES_PASSWORD`, `SUPPLIER_LOGIN` и `SUPPLIER_PASSWORD_HASH`; host-адрес `DATABASE_URL` из setup предназначен для локальной разработки и переопределяется Compose внутри приложения.

Проверьте свободный порт, ресурсы и отсутствие чужого checkout. Стек использует общий maintenance lock, чтобы не пересечься с обслуживанием других приложений. Не удаляйте lock-файл и не снимайте чужую блокировку. При занятой блокировке отложите запуск.

```sh
ssh qustust@100.126.73.77
cd /home/qustust/projects/lunch-together
docker compose config --quiet
flock -n /home/qustust/projects/libnode-backups/automatic/.automation.lock sh -eu -c '
  cd /home/qustust/projects/lunch-together
  docker compose build app
  docker compose up -d --wait
  docker compose ps
  curl --fail --silent http://127.0.0.1:3080/api/health
'
```

При старте приложения автоматически применяются его SQL-миграции под advisory lock. В пустой базе создаётся первая учётная запись поставщика из bootstrap-хеша и пример меню на следующий день по Алматы. Вымышленные участники и оплаты не создаются; повторный старт не сбрасывает данные и пароль.

После первого входа поставщик может сменить пароль, отменить пример сбора и создать свой с актуальным меню, адресом, реквизитами и сроками. Смена пароля в кабинете инвалидирует все сессии; bootstrap-хеш в `.env` не является способом сбросить пароль существующего поставщика.

## Подключение reverse proxy

Домен и сертификат настраивает владелец. Для рабочего входа поставщика нужен HTTPS. Для Nginx, работающего на этом же хосте, upstream — `http://127.0.0.1:3080`; передавайте исходный Host и протокол внешнего соединения:

```nginx
location / {
    proxy_pass http://127.0.0.1:3080;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
}
```

Этот пример заменяет присланный клиентом `X-Forwarded-For`. При подключении host Nginx через loopback контейнер видит доверенный gateway `172.16.80.1`. Приложение учитывает forwarded-заголовки только от адреса из `TRUST_PROXY`; не заменяйте его на `true`, все частные сети или произвольное число hops. Если proxy работает в другом месте, разрешите его точный исходящий IP/CIDR и отдельно проверьте маршрут. При прямой работе без proxy доверие можно выключить значением `TRUST_PROXY=0`.

`APP_ORIGIN` можно оставить пустым: приложение сравнивает Origin с текущими Host и протоколом запроса. Для единственного закреплённого домена можно задать его точный HTTPS origin без завершающего `/` и пересоздать только `app`. После этого мутации через другие origins будут отклоняться.

После настройки proxy проверьте вход и выход, Secure cookie на HTTPS, создание заявки, ручную оплату и кабинет на одном origin. Прямой внешний запрос к `3080` с поддельным `X-Forwarded-Proto` не должен считаться доверенным HTTPS-запросом. Не считывайте и не публикуйте токены cookie ради проверки.

## Обновление

Перед обновлением проверьте локальные сборку и тесты, серверный `git status --short`, свободное место, состояние контейнеров и состав миграций. Сохраните резервную копию перед изменением схемы. Доставку исходников, сборку, переключение и smoke-проверку выполняйте под общей блокировкой. Соседние контейнеры и их базы не затрагивайте.

Если checkout чистый, доступ к GitHub работает и новый commit совместим с текущими данными:

```sh
flock -n /home/qustust/projects/libnode-backups/automatic/.automation.lock sh -eu -c '
  cd /home/qustust/projects/lunch-together
  git pull --ff-only
  docker compose config --quiet
  docker compose build app
  docker compose up -d --no-deps --wait app
  docker compose ps
  curl --fail --silent http://127.0.0.1:3080/api/health
'
```

Сборка завершается до пересоздания приложения. `--no-deps` сохраняет работающий PostgreSQL. Приложение применяет свои pending migrations при запуске, поэтому проверяйте их до переключения; опасные изменения схемы требуют отдельного плана. Пересоздание одного контейнера приложения может кратко прервать запросы. Изменения пароля PostgreSQL требуют отдельной процедуры для существующей базы: изменение `POSTGRES_PASSWORD` в `.env` само по себе не меняет пароль внутри сохранённого тома.

Данные переживают обычное `up`/пересоздание и `down` без `-v`. **Не выполняйте `docker compose down -v` на рабочем стеке:** эта команда удаляет том с заказами, оплатами, возвратами и учётной записью поставщика. Тестовый `compose.test.yml` использует другой project и tmpfs; не подменяйте в его тестах адрес базы на production.

## Ручная резервная копия

Пример ниже создаёт сжатый логический backup только базы `lunch`, без остановки соседних приложений. Выполнять на сервере из каталога проекта под той же блокировкой; команды приводятся как инструкция и не означают, что backup уже создан.

```sh
flock -n /home/qustust/projects/libnode-backups/automatic/.automation.lock sh -eu -c '
  cd /home/qustust/projects/lunch-together
  umask 077
  mkdir -p backups
  chmod 700 backups
  docker compose exec -T db pg_dump -U lunch -d lunch -Fc > "backups/lunch-$(date -u +%Y%m%dT%H%M%SZ).dump"
'
```

Копии содержат данные участников и должны храниться закрыто, включая отдельную защищённую копию вне сервера. `backups/` исключён из Git. Перед использованием backup проверяйте восстановление в отдельной одноразовой базе; не восстанавливайте поверх рабочей базы без отдельного плана. Сохраняйте `.env` отдельно защищённым способом: дамп базы не включает конфигурацию контейнеров.
